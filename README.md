## Overview

**Smart Office — Meeting Room Booking System** is a complete meeting-room management concept for a Smart Office environment. The platform connects a web-based booking system with IoT devices installed in meeting rooms so that room availability and physical occupancy can be monitored in real time.

The system is designed around four major goals:

1. Prevent **double booking** and reduce cases where a room is physically empty but still appears unavailable.
2. Provide **real-time room occupancy status** using IoT sensors.
3. Reduce unnecessary energy consumption through **automatic control of lights and air conditioning**.
4. Collect and analyze room-usage data to support **organizational planning and facility management**.

The project documentation defines:

- **5 core modules**
- **3 user roles**
- **24+ API endpoints** as stated in the project overview
- A **6-month development timeline**

---

## Project Goals

### 1. Reduce Double Booking

The system provides real-time room availability and a centralized booking calendar so employees can check room schedules before creating a reservation.

### 2. Detect Real-Time Occupancy

ESP32-based IoT nodes use PIR sensors to detect whether a meeting room is occupied. The resulting status is sent through MQTT to the backend and can be displayed on the web dashboard.

### 3. Automate Energy Usage

The system can automatically turn room equipment on before a scheduled meeting and turn it off when the room becomes empty after the meeting.

### 4. Improve Resource Planning

Historical booking, occupancy, sensor, and energy-related data can be analyzed through dashboards and reports.

# Core Features

The booking module covers the main user journey from finding an available room to editing or cancelling a reservation.

### Real-Time Room Search

Users can search for rooms using:

- Date
- Start time
- End time
- Required capacity
- Required equipment / amenities

The system then displays rooms that match the requested criteria and are available during the selected time.

### Calendar View

Room reservations can be viewed using:

- Weekly view
- Monthly view
- Per-room timelines

This makes it easier to understand room utilization and avoid scheduling conflicts.

### Recurring Bookings

Users can configure recurring meetings, such as:

> Every Monday at 09:00

Recurring reservations are represented using an **iCalendar RRULE**.

### Meeting Invitations

A booking can include attendees using:

- User IDs
- Email addresses

Invitation and calendar-related workflows are intended to integrate with email and Google Calendar.

### Edit and Cancel

Users can modify or cancel their own bookings. Related users can receive notifications when the booking changes.

### LED Display

An LED display installed outside the room can show:

# IoT Data Flow

The documented sensor data path is:

```text
ESP32
   │
   ▼
MQTT
   │
   ▼
Mosquitto MQTT Broker
   │
   ▼
Node.js Backend
   │
   ▼
WebSocket
   │
   ▼
Web Dashboard
```

### Flow Explanation

1. ESP32 reads sensor values.
2. ESP32 publishes the sensor payload to an MQTT topic.
3. Mosquitto receives the MQTT message.
4. The Node.js backend subscribes to the topic and processes the data.
5. The backend can persist data and calculate room state.
6. WebSocket pushes real-time updates to connected clients.
7. The dashboard updates room status without requiring a manual refresh.

# IoT Integration

## ESP32 Firmware Logic

The source project document provides a simplified Arduino-style firmware example.

```cpp
#include <WiFi.h>
#include <PubSubClient.h>
#include <DHT.h>

const char* DEVICE_ID = "ESP32-ROOM-A";
const char* MQTT_TOPIC_SENSOR = "office/room-a/sensor";
const char* MQTT_TOPIC_CMD    = "office/room-a/command";

void publishSensorData() {
  float temp = dht.readTemperature();
  bool  occ  = digitalRead(PIR_PIN);

  String payload = "{\"temp\":" + String(temp)
    + ",\"occupancy\":" + String(occ)
    + ",\"device\":\"" + DEVICE_ID + "\"}";

  client.publish(MQTT_TOPIC_SENSOR, payload.c_str());
}

void onMessage(String topic, String message) {
  if (message == "light_on") digitalWrite(LIGHT_RELAY, HIGH);
  if (message == "ac_on")    digitalWrite(AC_RELAY, HIGH);
}
```

This example demonstrates two directions of communication:

- **Sensor → MQTT:** publish room state and environmental data.
- **Server → MQTT:** send control commands to the room device.

> The firmware shown in the source document is explicitly a simplified example, not a complete production firmware implementation.

### Sensor Data

### Device Commands

```text

```

**Direction:** Server → Device

**Purpose:** Send commands such as turning lights or air conditioning on/off.

---

### Device Status


**Purpose:** Report online/offline heartbeat information.

---

### LED Display

```text
office/{room-id}/display
```

**Direction:** Server → Device

**Purpose:** Send information to be shown on the room's LED display.

# Automation Rules

The system defines four main automation scenarios.

## Pre-Meeting

**5 minutes before the scheduled meeting:**

```text
Turn ON air conditioning
Turn ON lights
Update LED display
```

---

## No-Show Cancellation

**10 minutes after the meeting start:**

```text
PIR = 0
        ↓
No occupancy detected
        ↓
Cancel booking automatically
        ↓
Send notification
```

---

## Post-Meeting

After the scheduled meeting ends:

```text
Meeting time expired
        +
PIR = 0
        ↓
Turn OFF lights
Turn OFF air conditioning
        ↓
Set booking status = completed
```

---

## Overrun Alert

When:

```text
Meeting end time passed
        +
PIR = 1
```

the system should notify the next scheduled user that the room is still occupied.

# Security Architecture

## Authentication

The design specifies:

- JWT access token with a **15-minute** lifetime
- Refresh token with a **7-day** lifetime
- HTTP-only cookies
- bcrypt password hashing

## Authorization

The platform uses:

- Role-Based Access Control (RBAC)
- Route middleware guards
- Resource ownership checks
- Express rate limiting

## IoT Security

The architecture specifies:

- MQTT over TLS on **port 8883**
- Device authentication
- Per-device MQTT topic ACLs
- API keys for each ESP32
